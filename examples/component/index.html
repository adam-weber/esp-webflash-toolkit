esp-webflash-toolkit

Let your users flash firmware from a browser.

No toolchain, no drivers, no app install. Your user plugs in a USB cable, opens a web page, and clicks Flash. WiFi credentials, MQTT settings, device names — all configured in the browser and written to the device in one shot.

How it works

The toolkit uses the Web Serial API (Chrome, Edge, Opera) to talk directly to an ESP32 over USB. When a user clicks Flash, it downloads your firmware binary, generates an NVS partition from the form fields, and writes both to the device — the same thing esptool.py does, but in a browser tab.

Configuration values like WiFi SSID, passwords, and device names are stored in an NVS (Non-Volatile Storage) partition. Your firmware reads them on boot using standard ESP-IDF or Arduino APIs. No custom protocol, no serial monitor, no manual setup.

The simplest possible integration — just point at your GitHub repo:

html
<esp-flasher repo="your-name/your-repo" fields="wifi"></esp-flasher>

The component checks your repo for a flash-config.json. If there isn't one, it scans your latest GitHub release for .bin files and auto-detects the chip type from the binary header. Multiple .bin files become a variant dropdown automatically.

Which approach to use

There are two ways to use the toolkit. Pick the one that fits your project:

<esp-flasher> web component — Embed a flasher on your own site. Add a script tag and an HTML element to any page: your docs, your product page, a GitHub Pages site. The component handles the entire flow inside a shadow DOM, so it won't conflict with your styles. This is what you're reading about on this page.

Hosted flasher — A standalone flash page you don't have to build. Paste a firmware URL and pick your options, or point it at a flash-config.json in your GitHub repo. Share the link with your users. Good for quick testing, or if you don't have a website to embed on.

Installation

Load the component from a CDN. It self-registers the <esp-flasher> custom element — no imports, no build step.

html
<script src="https://cdn.jsdelivr.net/npm/esp-webflash-toolkit@latest/dist/esp-flasher-component.min.js"></script>

Compact mode

The default. Renders a single "Flash Firmware" button. When clicked, a modal opens with the full flash UI — connect, configure, flash, done. Great for embedding in docs or product pages without taking over the layout.

html
<esp-flasher
  firmware="https://github.com/user/repo/releases/latest/download/firmware.bin"
  chip="esp32s3"
  fields="wifi"
></esp-flasher>

Full mode

Set mode="full" to show the flash UI inline as a card — no button, no modal. Use this when flashing is the whole point of the page.

Here fields="wifi,device_name" renders three inputs: WiFi SSID, WiFi Password, and Device Name. The user fills them in, clicks Flash, and those values get written to the device alongside the firmware.

html
<esp-flasher
  firmware="https://github.com/user/repo/releases/latest/download/firmware.bin"
  chip="esp32"
  fields="wifi,device_name"
  mode="full"
></esp-flasher>

Config URL

For projects with multiple firmware variants (e.g. "Standard" and "Lite"), custom branding, or post-flash setup steps, put a flash-config.json in your repo and point the component at it. The component fetches the config and renders a variant dropdown automatically.

html
<esp-flasher
  config="https://raw.githubusercontent.com/user/repo/main/flash-config.json"
  mode="full"
></esp-flasher>

Fields

Fields define what your user configures before flashing. Set them with the fields attribute as a comma-separated list of presets. Each preset expands into one or more form inputs that get written to the device's NVS partition.

PresetForm inputsNVS keys written
wifiWiFi SSID, WiFi Passwordwifi_ssid, wifi_pass
mqttMQTT Host, MQTT User, MQTT Passwordmqtt_host, mqtt_user, mqtt_pass
device_nameDevice Namedevice_name

Combine them freely: fields="wifi,mqtt,device_name" renders all five inputs. If you don't need any config, omit the attribute entirely — the component will just flash the binary with no form.

You can also define custom fields through the config attribute or config-data for keys not covered by the presets.

Events

Listen for flash lifecycle events directly on the element. Use these to update your own UI, trigger analytics, or chain post-flash logic.

javascript
const el = document.querySelector('esp-flasher')

el.addEventListener('esp-flasher:connected', (e) => {
  console.log('Chip:', e.detail.chipType)
  console.log('MAC:', e.detail.macAddr)
})

el.addEventListener('esp-flasher:complete', () => {
  console.log('Done!')
})

el.addEventListener('esp-flasher:error', (e) => {
  console.log('Error:', e.detail.message)
})
EventDetailDescription
esp-flasher:connected{ chipType, macAddr }Device connected and identified
esp-flasher:complete{}Flash finished successfully
esp-flasher:error{ message }An error occurred during the process

Theming

Override CSS custom properties on the element to match your site's design. The component picks these up automatically — no JavaScript needed.

css
esp-flasher {
  --c-accent: #6366f1;
  --c-accent-hover: #4f46e5;
  --c-surface: #ffffff;
  --c-text: #09090b;
  --c-border: #e4e4e7;
}
PropertyDefaultControls
--c-accent#6366f1Buttons, links, focus rings, progress bar
--c-accent-hover#4f46e5Button and link hover states
--c-bg#fafafaStatus box and input backgrounds
--c-surface#ffffffCard and modal surface
--c-text#09090bPrimary text
--c-text-2#71717aSecondary text, descriptions
--c-border#e4e4e7Card borders, input borders

When loading config via URL, the branding.primaryColor field automatically maps to --c-accent, and branding.theme: "dark" flips all color variables to a dark palette. The theme attribute takes priority over branding.theme — set theme="auto" to follow the user's system preference.

Programmatic access

The component exposes its internal ESPFlasher instance on the .flasher property. Use it to set config values, read state, or control the flash process from JavaScript.

javascript
const el = document.querySelector('esp-flasher')

// Set config values before or during use
el.flasher.setConfig({ wifi_ssid: 'MyNetwork', wifi_pass: 'secret' })

// Read current config state
const config = el.flasher.getConfig()

// Get the field schema
const schema = el.flasher.getSchema()

Reading config in firmware

When you flash with fields="wifi,device_name", the component writes those values to an NVS (Non-Volatile Storage) partition on the device. Your firmware reads them back using standard ESP-IDF APIs — no special library needed.

All values are stored in a namespace called "config" at partition offset 0x9000. The NVS keys match the field names exactly:

Field presetNVS keys writtenType
wifiwifi_ssid, wifi_passstring
mqttmqtt_host, mqtt_user, mqtt_passstring
device_namedevice_namestring

Key things to know:

ConceptValueNotes
Namespace"config"All fields are stored under this NVS namespace
Partition offset0x9000Must match your partition table's NVS offset
Partition size0x6000 (24KB)Default size, configurable via config
Key length15 chars maxNVS keys are case-sensitive, alphanumeric + underscore
FormatESP-IDF NVSStandard binary format — no custom parser needed

The NVS partition is written alongside the firmware in a single flash operation. Your firmware just needs to call nvs_flash_init() (or Preferences.begin() in Arduino) and read the keys — nothing else to configure.
